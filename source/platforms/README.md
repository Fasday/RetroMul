# Добавление ядра и интеграция платформы

Инструкция охватывает аппаратную реализацию, адаптер, загрузку носителей,
GUI, настройки, ввод и периферию. Для нового ядра добавляются две папки
с одинаковым именем: `source/cores/<id>` и `source/platforms/<id>`.
Аппаратная реализация находится в `cores`, вся интеграция — в `platforms`.
Общие реестры и контроллеры для этого не редактируются; точка подключения —
явный вызов класса платформы в `RetroMul.Platforms`.

## Порядок добавления нового ядра

### Идентификаторы и файлы

Сначала выберите постоянные значения. В примере платформа называется
`example`, регистрация ядра — `EXAMPLE`, профиль настроек — `Example`,
владелец конфигурации и ID страницы — `example`. Эти значения могут
различаться; одинаковое написание здесь упрощает пример.

| Значение | Где используется |
| --- | --- |
| ID платформы | `RegisterPlatform`, `IEmulationCore.SystemId`, GUI и ввод |
| ID регистрации ядра | `TEmulationCoreRegistration`, `TCoreMatch`, приоритеты распознавания |
| `SettingsProfile` | Выбор класса страницы через `RegisterSettingsProfile` |
| `SettingsCoreId` | Общая конфигурация моделей и имя INI через `IStorage.ConfigFile` |
| ID страницы | `RegisterPlatformPresentation`, каталог и черновики; `main` зарезервирован |
| Токен и версия снимка | Проверка совместимости аппаратного состояния в загрузчике снимков |

Константы интеграции объявляйте в `RM.Platforms.<платформа>`.
Константы, используемые аппаратным ядром, размещайте в его модулях
типов или картриджа, чтобы ядро не зависело от клиентских `RM.*`.
Пополнять `ROM_SYSTEM_*`, `ROM_CORE_ID_*` или общее перечисление не требуется.
Для ID платформы и конфигурации выбирайте пригодные для имён файлов значения.
Не меняйте ID, папки, ключи и токены уже выпущенной платформы при её расширении.

Рекомендуемое расположение:

```text
source/cores/example/Example.*.pas
source/platforms/example/Core.Platforms.Example.Adapter.pas
source/platforms/example/RM.Platforms.Example.pas
source/platforms/example/RM.Platforms.Example.Settings.pas
```

Специальные обработчики добавляются рядом с существующими:
`RM.Platforms.Example.Input`, `RM.Platforms.Example.Session`,
`RM.Platforms.Example.SettingsHandler`, `RM.Platforms.Example.Window`,
`RM.Platforms.Example.Help`, `RM.Platforms.Example.Devices` и другие по необходимости.
Адаптеры и вспомогательные модули не должны импортировать модуль регистрации
`RM.Platforms.Example`: регистрация отделена от аппаратуры и адаптера.
Импорт класса платформы сам по себе не регистрирует её: нужен явный вызов
`TExamplePlatform.RegisterPlatform`.

### Именование и объединение модулей

Порядок частей имени: `<слой>.Platforms.<семейство>.<назначение>`.
`Core.Platforms.*` содержит адаптеры, форматы ROM и воспроизведение;
`RM.Platforms.*` — регистрацию платформы и интерфейс клиента.
Точка регистрации сохраняет имя `RM.Platforms.<семейство>` без суффикса.
Например: `Core.Platforms.NES.Adapter`, `RM.Platforms.NES.Settings`,
`RM.Platforms.NES.Input`, `RM.Platforms.NES.Devices`.
`Settings` означает страницы, `SettingsHandler` — применение настроек сессии.

Модули объединяются только внутри одной папки платформы. `Gamepads` содержит
все существующие классы раскладок семейства; `Devices` может объединять
создание устройств, привязки и выноски. Небольшие обработчики ввода и сессии
DC/ZX собраны в `Runtime`. Крупные обработчики NES остаются раздельными.
Отдельные страницы моделей объединены внутри SG1000 и SMS; общая база
настроек Sega остаётся отдельным модулем SG1000. Межплатформенное наследование
GB/GBC/GBA и использование общих модулей других семейств не объединяются.
Имена классов, строковые ID, профили и ключи сохранённых настроек сохраняются.

### Явная регистрация всех частей платформы

Платформенный модуль не должен регистрировать страницы, форматы или сервисы
при одном импорте. `RegisterPlatform` — единственная точка подключения;
он вызывает приватные методы класса и защищён от повторного выполнения.

- Классы страниц определяются в `RM.Platforms.<семейство>.Settings`,
  а `RegisterSettingsProfile`/`RegisterSettingsPlatform` вызываются из
  `RegisterClient` соответствующего класса платформы. Общая базовая страница
  другой платформы может использоваться без регистрации её собственного профиля.
- Функции чтения и нормализации остаются в `Core.Platforms.<семейство>.RomFormat`.
  Регистрации MD, N64 и SNES выполняет приватный `RegisterRomFormats` класса
  платформы перед `RegisterCore`. Импорт функций сам по себе реестры не меняет.
- GB и GBC независимо вызывают общий идемпотентный `RegisterGBXReader` из своих
  `RegisterRomFormats`. Он устанавливает один общий legacy-декодер GBX и
  не регистрирует метаданные, ядро или страницу GB. Допустим любой порядок
  подключения, а также только одна из этих платформ.
- Рендер Game & Watch устанавливается в `TGWPlatform.RegisterPlatform` через
  `CreateGWArtworkRenderer`. Во вспомогательном модуле остаётся только
  освобождение ссылки в `finalization`; при импорте рендер не устанавливается.

### Клавиатуры

Общий контракт `Core.Input.Keyboard.IEmulationKeyboard` принимает
`THostKeyboardKeys` — массив состояний 256 клавиш. Он не импортирует платформы.
Адаптер каждой платформы сам преобразует эти коды в свою аппаратную матрицу
или HID-отчёт. У DC преобразование находится в `Core.Platforms.DC.Keyboard`.

`RM.Keyboard.TKeyboardControl` содержит общее подключение touch-ввода;
матричные клавиатуры NES и Miracle Piano наследуют эту базу, сохраняя свои
коды, индикаторы и отрисовку. `TScreenKeyboard` добавляет общий механизм
рисования, контактов и фиксируемых клавиш; раскладки задают его наследники
в `RM.Platforms.SG1000.Keyboard`, `RM.Platforms.MSX.Keyboard`,
`RM.Platforms.SMS.Keyboard` и `RM.Platforms.ZX.Keyboard`.
Две матричные клавиатуры NES находятся в `RM.Platforms.NES.Keyboard`.
В общей реализации нет выбора по конкретной платформе или режима Spectrum.

Платформа явно вызывает `RegisterPlatformKeyboard('example', TExampleKeyboard)`
из своего `RegisterPlatform`/`RegisterClient`. Общие `RM.Keyboard.Input`,
`.Session`, `.Settings`, `.Window` работают только с контрактом и реестром.
Без регистрации клавиатура не создаётся; до выбора платформы контрол отсутствует.
При смене класса снимаются захват FMX и обработчики, очищается удерживаемый ввод,
после чего прежний контрол отсоединяется и передаётся в `Release`.
Не требуется создавать клавиатуру для платформ, у которых её нет.

### Аппаратная реализация и адаптер

Реализуйте аппаратуру в `source/cores/example`, повторно используя подходящие
компоненты RetroMul. Поведение проверяйте по документации оборудования и
диагностическим ROM. DSP Emulator служит перечнем систем и дополнительным
источником, но не эталоном корректности. Готовые сторонние бинарные библиотеки
не подключаются без прямого запроса пользователя.

`Core.Platforms.Example.Adapter` реализует `IEmulationCore` и отделяет аппаратуру от
фронтендов. Предусмотрите запуск/остановку, паузу, сброс, очистку и чтение ввода,
выдачу кадров, ошибки и конфигурацию. Возвращайте свой канонический `SystemId`.
Остановка должна завершать работу потока и его обращения к ресурсам фронтенда.
Пиксели `TEmulatorFrame` имеют формат premultiplied ARGB, строки идут подряд.

Конфигурацию удобно наследовать от `TEmulatorConfigBase`, реализовав свои
`LoadCoreSettings` и `SaveCoreSettings`. Возможности подключайте интерфейсами:
`IEmulationLiveSettings`, `IEmulationInputPorts`, `IEmulationSnapshotLocation`,
`IEmulationDiscControl`, интерфейсами мыши, указателя, вибрации и датчиков.
Специальный протокол устройства объявляйте в модуле адаптера; его вызывает
платформенный обработчик ввода. Новое ядро не требует нового метода в `RM.Main`.

Сохранения размещайте через `IStorage` и существующие средства `Core.SavePaths`.
Токен снимка и версию его содержимого определяет ядро; ID регистрации сам
по себе не записывает заголовок снимка. Не сохраняйте числовой индекс платформы.
При изменении формата обеспечьте чтение прежней версии или явный отказ.
`SupportsSnapshots` должен соответствовать реализованным операциям.

### Регистрация платформы и загрузчика

В `RM.Platforms.Example` создайте класс `TExamplePlatform` со статическими
классовыми методами. Единственный публичный метод `RegisterPlatform` объединяет
регистрацию ядра, метаданных, сервисов и GUI. Вспомогательные методы приватные.
Ниже фрагмент после реализации `TExampleCoreAdapter`; `NEW!` — условная
сигнатура примера, которую нужно заменить проверкой реального формата.

```pascal
type
  TExamplePlatform = class
  strict private
    class var FRegistered: Boolean;
    class function Recognize(Context: TCoreLoadContext): TCoreMatch; static;
    class procedure RegisterCore; static;
    class procedure RegisterClient; static;
  public
    class procedure RegisterPlatform; static;
  end;

class function TExamplePlatform.Recognize(Context: TCoreLoadContext): TCoreMatch;
begin
  Result := nil;
  if not Context.Signature(0, 'NEW!') then Exit;
  Result := ImageMatch(Context, 'EXAMPLE',
    function(const Data: TBytes; Input: TStream): IEmulationCore
    begin
      Result := TExampleCoreAdapter.Create(
        Input, Context.EffectiveStorage, Context.RomName);
    end, False, 'example');
end;

class procedure TExamplePlatform.RegisterCore;
begin
  TPlatformRegistry.RegisterPlatform(
    'example', 'Example Console', 'Example', 'Vendor',
    'Example Console', 'example', ['example'],
    ['.example', '.zip', '.7z'], 'Example', 'example', 2);
  var Registration := TEmulationCoreRegistration.Create('EXAMPLE', ['.example']);
  Registration.Add(TCoreLoadStage.Header, 100, Recognize);
  RegisterEmulationCore(Registration);
end;

class procedure TExamplePlatform.RegisterClient;
begin
  RegisterSettingsProfile('Example', TExampleSettings);
  RegisterPlatformPresentation('example', 'example', PlatformIconExample);
  // Register input, gamepads and the required handlers here.
end;

class procedure TExamplePlatform.RegisterPlatform;
begin
  if FRegistered then Exit;
  RegisterCore;
  RegisterClient;
  FRegistered := True;
end;
```

`RegisterPlatform` получает полный список внешних форматов для библиотеки
и диалога открытия, включая реально поддерживаемые архивы.
`TEmulationCoreRegistration.Create` получает расширения образов внутри архивов.
`ImageMatch` в примере использует нативные байты без специальной нормализации.
Для собственного преобразования данных используйте свой загрузчик, сохраняя
границы чтения и ограничения размера. Детали этапов приведены ниже.

Проба возвращает `nil` для чужого формата и отложенный `TCoreMatch` для своего.
Не запускайте поток эмуляции в распознавателе. Проверяйте длины перед чтением
полей; не присваивайте общие `.bin` или `.iso` только по расширению.
Согласуйте приоритет с существующими правилами для пересекающихся форматов.

ZIP не нужно повторно разбирать в каждом ядре: общий механизм проверяет
кандидатов зарегистрированными распознавателями, в том числе по содержимому
при неизвестном расширении. Для ROM-сета нужен обработчик `Container`,
для потокового или составного носителя — подходящий `Source`/дисковый загрузчик.
Другие архивные контейнеры подключаются через `Core.MediaArchive` для всех ядер.
Проверьте неоднозначные архивы и ограничения, описанные в разделе об архивах.

Входным потоком владеет вызывающий код, `Context` принадлежит фабрике.
До возврата адаптер должен
скопировать нужные данные, удержать `Storage` или принять диск через `TakeDisc`.
Для повторного открытия файлов преобразованного архива используйте
`EffectiveStorage`; исходный `RomName` сохраняет идентичность игры и сохранений.

### Страница настроек

Создайте `RM.Platforms.Example.Settings` в `source/platforms/example`. Наследуйте страницу от
`TSettingsPlatform` и заполняйте `Configuration`, `Video`, `Audio`,
`Peripherals`/`Expansion` через `TSettingsPageBuilder`. Для нестандартных
устройств переопределите `PortOptions`; используйте устойчивые ID полей и
ключи INI. Не ищите контролы по именам через `FindComponent`.

В `TExamplePlatform.RegisterClient`, вызываемом из `RegisterPlatform`,
выполните один из вариантов. В модуле страницы оставьте только её класс:

```pascal
RegisterSettingsPlatform('example', TExampleSettings);
// Или RegisterSettingsProfile('Example', TExampleSettings)
// для канонических платформ с таким SettingsProfile.
```

Каталог создаёт страницу после регистрации её метаданных и представления.
Если несколько моделей разделяют настройки, согласуйте `SettingsCoreId`
и ID страницы и регистрируйте страницу владельца конфигурации.
Самостоятельную страницу нельзя зарегистрировать для псевдонима вместо
канонического владельца. Даже без специальных полей можно использовать
обычную страницу на базе `TSettingsPlatform`.

### Подключение GUI

В том же `RM.Platforms.Example` подключите `RM.Platforms.Example.Settings`, свои
геймпады и обработчики. Приватный метод `TExamplePlatform.RegisterClient`
выполняет GUI-регистрации и вызывается только из `RegisterPlatform`.
Для обычного геймпада отдельные обработчики не нужны: можно явно зарегистрировать
базовые классы, как это делает `RM.Platforms.GBA`.

| Регистрация | Что передать |
| --- | --- |
| `RegisterPlatformPresentation` | Иконку TPath и строковый ID страницы |
| `RegisterPlatformGamepads` | Существующий или свой `TPlatformGamepad` и варианты устройств |
| `RegisterPlatformInput` | Маски и имена кнопок, начальные клавиши, этапы загрузки и фильтр |
| `RegisterPlatformInputHandler` | `TPlatformInputHandler` либо свой обработчик устройств |
| `RegisterPlatformSessionHandler` | `TPlatformSessionHandler` либо подключение периферии к сессии |
| `RegisterPlatformWindowLayout` | `TPlatformWindowLayout` либо размеры, отступы и порядок своих контролов |
| `RegisterPlatformSettingsHandler` | `TPlatformSettingsHandler` либо применение своих настроек и периферия |
| `RegisterPlatformControlsHelp` | `TPlatformControlsHelp` либо собственная справка и команды |
| `RegisterPlatformDeviceCallouts` | `TPlatformDeviceCallouts` либо геометрия и дополнительные кнопки |
| `RegisterPlatformSettingsDevices` | `TPlatformSettingsDevices` либо создание устройств в настройках |
| `RegisterPlatformPalettePreview` | Только при собственном предпросмотре палитры |

Для полноценного игрового GUI нужны представление, класс геймпада, описание
ввода и страница настроек. У остальных реестров есть базовое поведение;
переопределяйте нужные методы. Базовая фабрика геймпадов не создаёт класс
за неизвестную платформу, а описание ввода без регистрации не даёт маску кнопок.
Предпросмотр палитры без провайдера использует общий цветовой образец.

Собственный геймпад наследуйте от `TPlatformGamepad` и реализуйте `BuildLayout`.
Иконку можно хранить в собственном модуле: пополнять общий список иконок
не обязательно. Для обычных значков используйте Fluent/TPath, для уникальной
графики устройств допустим собственный рисунок. FMX-разметку стройте через
`Align`, `TLayout`, `Margins` и `Padding`; статические элементы сохраняйте
в FMX. Статические иконки интерфейса также сохраняйте в FMX.
Компоненты именуйте по классу и назначению.

### Клавиши и специальные устройства

В `TPlatformInputDefinition` задайте кнопки, варианты устройств и начальные
клавиши через `LoadLegacyKeys` или свои этапы загрузки. Нулевые клавиши
не создают назначений, поэтому для игры с клавиатуры задайте явную карту.
ID устройств сопоставляются с учётом регистра; поддержите выбранные
`auto`, `none`, `pad-*` или зарегистрируйте точные собственные варианты.

`FilterBinding` задаёт разрешение действия и ключ источника ввода.
Новое ядро по умолчанию не включает `UseSharedBindingRules` и не вызывает
`LoadSharedLegacyBindings`: эти механизмы нужны существующим профилям для
сохранения исторического поведения. `AfterLoadBindings` выполняется и после
JSON; этапы `BeforeLegacyBindings`/`AfterLegacyBindings` — только при импорте INI.
Не меняйте коды действий уже сохранённых привязок. Дополнительные действия
объявляйте у платформы, не расширяя общий `TEmulatorButton` для её частных кнопок.

Чтение специального устройства выполняет зарегистрированный обработчик:
`CombineInput`, `UpdateInput`, `PollInput`, `ForwardKey` и другие методы
`TPlatformInputHandler`. Он обращается к интерфейсу своего адаптера.
Для обычного логического геймпада достаточно базового пути.

Состояние периферии храните в своём объекте с подсчётом ссылок через
`Context.Data`/`SetData` под уникальным ключом. `RM.Main.State` новых полей
не требует. `Initialize` создаёт устройства, `Finalize` отключает их и
освобождает даже при внешних ссылках на объект состояния. Общий механизм
обеспечивает обратный порядок завершения, повторные вызовы и частичную
инициализацию. Контролы должны иметь владельца и защиту ссылок при удалении.

Перед отложенным `Release` снимите собственные события, native/touch-слушателей,
удерживаемый ввод и захват средствами FMX, очистите `TagObject` и имена.
Заимствованные ссылки на окно и поля страницы не сохраняйте после отключения.
Класс обработчика не должен хранить общее изменяемое состояние разных окон.

Сессию, размещение, применение настроек, справку, выноски и карточки устройств
дополняйте соответствующими провайдерами из таблицы. Обычные горячие клавиши
идут в справке первыми; платформа может показать их заблокированными.
Её дополнительные команды добавляются после общих. Контракты методов и
примеры собраны в [документации GUI](Client.md).

### Включение в приложения и проверка

Создайте `source/platforms/example/RM.Platforms.Example.pas` с классом
`TExamplePlatform`. Он объединяет регистрацию ядра и интерфейса.
Отдельный модуль `Core.Register` и файлы деклараций не нужны.

Все поисковые пути и `DCCReference` перечислены непосредственно в `.dproj`
относительно его папки. Добавьте туда относительные пути новых подпапок ядра
и интеграции, например `..\..\source\cores\example` и
`..\..\source\platforms\example`, и ссылки на новые модули.
Существующие значения `$(DCC_UnitSearchPath)` сохраняйте.

Состав приложения задаётся вручную в одном обычном модуле
`apps/retromul/RetroMul.Platforms.pas`. Он подключён через `uses ... in ...`
в `.dpr` и зарегистрирован в `.dproj`. Добавьте `RM.Platforms.Example`
в его `uses`, а `TExamplePlatform.RegisterPlatform` — в `initialization`.
В самих модулях платформ автоматической регистрации в `initialization` нет.
GUI-зависимости и методы являются обычной частью классов платформ.
Терминал больше не является целевой конфигурацией для развития и проверки интеграции.
Генерации исходников при сборке и дополнительных файлов настройки сборки нет.

Для отключения платформы удалите её вызов `RegisterPlatform` и импорт
из `RetroMul.Platforms`. Само наличие файла в `DCCReference` или поисковом пути
не включает регистрацию. Общие реестры и контроллеры менять не требуется.
Для проверки пустого состава удалите вызовы регистрации и импорты платформ;
`System.SysUtils` оставляет секцию `uses` корректной. После изменения состава
выполните полную пересборку (Build), чтобы исключить устаревшие DCU.

Сохраняйте полное соответствие имён папок верхнего уровня в `cores`
и `platforms`. Папка без интеграции содержит README без фиктивной регистрации.
Горячая загрузка модулей не используется. Pascal сохраняйте в UTF-8 с BOM.

Проверьте результат:

1. Распознавание прямого ROM, ZIP/поддерживаемого другого архива,
   неизвестного расширения, чужой сигнатуры, усечённых данных и нескольких
   подходящих образов. Пробы не должны создавать эмулятор.
2. Первый запуск без игры, библиотеку, фильтр файлов, настройки и справку.
   До ROM `SystemId` пустой; старт не выбирает новое ядро или GB автоматически.
3. Сохранение/повторную загрузку настроек, клавиатуру, контроллеры, оси,
   смену устройств и отпускание ввода после диалогов/потери фокуса.
4. Старт, паузу, сброс, смену игры, остановку, закрытие, батарейные сохранения,
   снимки и autosave в пределах заявленных возможностей ядра.
5. Удаление только точки подключения нового модуля из состава приложения:
   платформа, правила загрузки и GUI исчезают, остальные ядра продолжают работать.
   Отдельно проверьте пустой состав, иной порядок подключений и запуск без GB.
6. Debug/Release для Win32/Win64 у GUI; мобильные и прочие
   платформы — при заявленной поддержке. Сравните интерфейс на узком и широком
   окне. Логи, временные ROM и проверки храните в `codex-work`.

Эталоны структуры: [TNESPlatform](nes/RM.Platforms.NES.pas) для ROM,
[TPS1Platform](ps1/RM.Platforms.PS1.pas) для более сложных носителей,
[RM.Platforms.GBA](gba/RM.Platforms.GBA.pas)
для базового GUI и
[RM.Platforms.NES.Input](nes/RM.Platforms.NES.Input.pas)
для хранения и завершения работы периферии.

### Ограничения текущих контрактов

Регистрация статическая: состав меняется пересборкой, горячая выгрузка
не предусмотрена. Метаданные и общий ввод поддерживают 1–12 игроков.
Общий набор логических кнопок фиксирован; дополнительные кнопки и устройства
описываются собственными действиями, контролами и интерфейсами платформы.
Закрытого списка раскладок больше нет: `RegisterPlatformGamepads` выбирает
класс экранного устройства напрямую по строковому ID платформы и устройства.

Форматы образов реализованы в `GB.RomFormat`, `MD.RomFormat`, `N64.RomFormat` и
`SNES.RomFormat` соответствующих ядер. Проверка Realtec принадлежит MD.
Хеши известных образов находятся в `NES.RomHashes` и `SNES.RomHashes`.
Общее чтение потока `ReadRomData` находится в `Core.Storage`.
Контракты нормализаторов и `TRomFormatInfo` находятся в `Core.EmulatorRegistry`:
пустой `Encoding` означает исходные байты, остальные строковые ID объявляются
своей платформой и регистрируются через её `RegisterPlatform`.
Общего перечисления кодировок нет.
Константы пределов размера образа и copier-заголовка принадлежат каждой
платформе отдельно и находятся в её модулях интеграции или картриджа.
Общие загрузчики и хранилище имеют собственные пределы по умолчанию. Поля `FourScore` и `LegacyZapper`
в `TCoreInputPorts` сохраняют исходный API аппаратных модулей.
Добавлять в общие модули идентификаторы, константы или поля нового ядра не нужно:
новые константы принадлежат его модулям, частные параметры ввода передаются через
`TCoreInputPorts.Options`, `Option` и `SetOption`.

Отсутствие регистрации означает отсутствие платформы в приложении;
использование её аппаратных классов другим адаптером само по себе допустимо.

## Справочник регистрации

Каждый класс в `RM.Platforms.*` объединяет метаданные, распознаватели,
создание адаптера, сервисы и GUI-регистрации. Публичный статический метод
`RegisterPlatform` вызывает приватные классовые методы в прежнем порядке
и защищён от повторного вызова. Модуль приложения `RetroMul.Platforms` импортирует
эти классы и явно вызывает их `RegisterPlatform` при инициализации приложения.
См. [интеграцию GUI](Client.md).
`Core.Platforms`, `Core.EmulatorFactory` и `Core.EmulatorRegistry` не содержат
автоматического списка подключённых платформ или ядер.

Регистрация отделена от адаптера намеренно: адаптеры могут использоваться
другими адаптерами или интерфейсом приложения. Например, наследование адаптера
GBC от GB не должно автоматически включать регистрацию GB.

Для нового ядра потребуется:

1. Создать адаптер, реализующий `IEmulationCore`.
2. Создать класс в `RM.Platforms.<имя>`, описать платформы, распознаватели и создание
   адаптера. В расширениях платформы указывать полный список форматов, включая
   поддерживаемые архивы; реестр не дополняет список по типу ядра.
3. Добавить один публичный статический метод `RegisterPlatform`, который
   вызывает регистрацию ядра, сервисов и GUI; повторный вызов должен быть безопасен.
4. Указать относительные пути и ссылки на модули в `.dproj`, добавить
   импорт и вызов `RegisterPlatform` в `RetroMul.Platforms` и пересобрать приложение. Общие реестры,
   контроллеры и `.dpr` не изменяются.

Отсутствие вызова `RegisterPlatform` исключает платформы класса из библиотеки,
фильтра файлов и настроек, а его правила — из выбора и проверки содержимого архивов.
Пустые реестры допустимы: неподдерживаемый файл приводит
к `EReadError`. Регистрации рассчитаны на статическую инициализацию до начала
загрузки игр; добавления и удаления во время работы нет.

## Метаданные платформ

Один модуль может зарегистрировать несколько платформ своего ядра: например,
Mega Drive / Sega CD / 32X или три модели MSX. Метаданные включают ID, названия,
производителя, поисковые строки, папки сканирования, расширения, параметры
настроек и число портов. Порядок выдачи всегда определяется производителем
и названием и не зависит от порядка подключения модулей.

Платформа определяется только строковым `TPlatformInfo.Id`, например `nes`,
`md` или собственным ID нового ядра. Общего перечисления платформ нет;
новое ядро объявляет ID у себя и передаёт его в `RegisterPlatform` и
`TRomFormatInfo.SystemId` (параметр `SystemId` функции `ImageMatch`).
Пустая строка означает нераспознанную платформу, а не элемент реестра.

При регистрации ID приводится к нижнему регистру без крайних пробелов;
поиск нечувствителен к регистру. `Find` проверяет наличие платформы,
`Require` сообщает об отсутствии, `CanonicalId` разрешает псевдоним либо
возвращает нормализованный входной ID, не регистрируя его.
Папки и старые строковые псевдонимы по-прежнему разрешаются через реестр;
дополнительные псевдонимы регистрируются через `RegisterAlias`.
Псевдонимы AES принадлежат модулю Neo Geo и отсутствуют без него.
Они не создают дополнительных платформ в `All`.

Существующие ID, `Folder`, `SettingsCoreId` и токены
`ROM_CORE_ID_*` менять при таком подключении нельзя: они определяют прежние
настройки, библиотеку и пути сохранений. Заголовок снимка `RMSNAP01` хранит
строковый токен ядра, а не порядковое значение перечисления. Формат снимков,
версии аппаратного состояния и имена файлов сохранений не менялись;
миграция данных не требуется. Для нового ядра константы ID можно объявить
в его собственном модуле, без изменения общего списка констант.

Провайдеры настроек могут инициализироваться раньше метаданных или отображения:
каталог хранит их заявки и применяет их при готовности обеих частей. Если модуль ядра не
подключён, его заявки остаются без страниц. Для уведомлений используется
`AddRegistrationListener` / `RemoveRegistrationListener`; реестр не зависит
от интерфейса или настроек. Возвращаемые метаданные содержат копии массивов,
которые можно менять без изменения самого реестра.

## Этапы распознавания

| Этап | Назначение |
| --- | --- |
| `Source` | Потоковые образы, диски, исполняемые файлы и плейлисты |
| `Container` | Архив целиком, например аркадный ROM-сет |
| `Image` | Извлечённый образ, специальные носители и подсказки расположения |
| `Header` | Сигнатуры и кодировка ROM |
| `OverrideHint` | Явное расширение для форматов без обязательной сигнатуры |

Внутри этапа меньшее значение `Priority` проверяется раньше. При равенстве
используется ID регистрации. Порядок `uses` не определяет выбор ядра.
Распознаватель возвращает `nil` либо `TCoreMatch` с отложенным созданием
адаптера. Пробы не должны создавать работающие эмуляторы. Ошибка уже
распознанного формата передаётся вызывающему коду.

`ImageMatch` предоставляет поток байтов, ограничение размера и при необходимости
нормализацию ROM. Его параметр `SystemId` необязателен: отдельному новому
распознавателю достаточно собственного ID и функции создания адаптера.
`HeaderFormat` и `HeaderRecognized` доступны подсказкам расширения после этапа
`Header`. Наличие совпадения определяется через `HeaderRecognized`;
строковый ID формата не ограничен набором уже реализованных платформ.

## Архивы и владение данными

ZIP проверяется сначала как составной набор, затем как набор отдельных образов.
Для записей архива используются те же зарегистрированные распознаватели всех
этапов, включая `Source`. `ArchiveExtensions` позволяет объявить расширения
форматов без обязательной сигнатуры; общего списка расширений ROM нет.
Файл с неизвестным расширением также проверяется по содержимому.

Провайдер может задать дополнительные кандидаты, предпочтение между образами,
подсказку имени и разрешение выбора варианта. Сохранены предпочтение дисков ZX
над снимками, TRD над SCL, выбор вариантов MSX и архивов 7z. В остальных случаях
несколько подходящих образов считаются неоднозначным архивом.

`Core.MediaArchive` приводит другие форматы к каноническому ZIP через
`RegisterMediaArchiveFormat`. Сейчас подключён 7z. Новый декодер подключается
отдельно и предоставляет поддержку всем ядрам, включая загрузчики ROM-сетов
и дисков. Для преобразованных архивов `Core.ArchiveStorage` сохраняет доступ
к данным при повторном открытии ядром, сохраняя исходный путь и идентичность
сохранений. Декодирование 7z сохраняет прежний предел 256 МиБ распакованных данных.

Одиночные ROM в архиве ограничены 64 МиБ. Составные диски и PSP используют
свои потоковые загрузчики и прежние ограничения. CD-архив содержит один
дескриптор CUE/GDI/MDS с дорожками либо один самостоятельный образ;
сопутствующие файлы должны лежать рядом с дескриптором внутри архива.
Вложенные архивы рекурсивно не перебираются.

Вызывающий код владеет входным `Stream`. Контекст живёт до завершения создания
адаптера. Адаптер должен скопировать необходимые байты, удерживать `Storage`
или принять диск через `TakeDisc`; заимствовать поток или контекст после
возврата фабрики нельзя. `RomName` остаётся исходным путём, а `SourceName`
описывает текущий образ или канонический контейнер.

## Дополнительные правила интеграции

Все регистрации ниже выполняют методы класса в `RM.Platforms.*` своей
платформы либо подключённые им специализированные провайдеры. Отсутствие регистрации сохраняет нейтральные значения клиента.

| API | Назначение |
| --- | --- |
| `RegisterSnapshotPolicy` | Версия снимка, допустимые старые версии, лимит размера и специальные сообщения об ошибках |
| `RegisterPlatformServices` | Правила библиотеки M3U/CUE/GDI, фоновая загрузка по расширению, старое именование сохранений, политика ввода терминала и выбор дополнительных документов |
| `RegisterRomNormalizer` | Собственное преобразование ROM; распознавание использует зарегистрированные правила фабрики |
| `RegisterCDMediaFormat` | Загрузчик нового дискового формата, необязательная проба содержимого и признак дескриптора/контейнера |
| `RegisterCDCompanionExtension` | Дополнительные файлы дискового образа в ZIP |
| `RegisterCDTrackAdjustment` | Платформенная коррекция расположения дорожек |
| `RegisterInputPortsReader` | Загрузка частных параметров портов из INI в `TCoreInputPorts.Options` |
| `TSettingsPlatform.PrepareSave` | Очистка и миграция настроек только своей платформы |
| `TPathSetting.FileFilter`, `PickerTitle` | Фильтр и заголовок выбора файла конкретного поля настроек |
| `TPlatformInputHandler.KeyPolicy` | Резервирование горячих клавиш; общие подсказки учитывают эту же политику |

Снимки существующих платформ сохраняют байтовый формат `RMSNAP01` и прежние
версии. Длинные и Unicode ID используют `RMSNAP02` с явным UTF-8 ID; допустимый
размер ID — до 4096 байт. Платформа самостоятельно повышает версию своего
сериализатора, не меняя общий модуль снимков.

Владение потоками и контролами остаётся явным. `TCDDisc.AddTrack` принимает
владение потоками дорожки. Данные периферии хранятся в контексте своего окна;
`Finalize` отключает события и освобождает устройства. При замене FMX-контролов
используйте `RM.Controls.Lifetime.RetireControl`, который снимает захват,
обработчики и заимствованные ссылки перед отложенным `Release`.

Для сложного ядра клиентская папка может содержать несколько модулей и
подпапок. Переиспользование аппаратуры и компонентов другой платформы
разрешено; импорт адаптера или компонента не должен автоматически регистрировать
владельца. Например, GBC переиспользует GB, а MSX и ZX — экранную клавиатуру.

Настройки читаются только из указанного файла. Если его нет, используются
значения по умолчанию; подстановка старого имени INI не выполняется.
